# 性能测量与万轨目标

目标负载是 10,000 条轨道**同时持续发声并各自运行非零混响**。项目可加载的轨道数、屏幕上的音符数、活动声音计数、CPU 离线吞吐和浏览器实时输出分别度量不同事项。

## 三类证据

| 测量 | 能说明 | 不能单独说明 |
| --- | --- | --- |
| Rust / WASM ABI 测试 | 插值、声像、混响隔离、边界和声音池行为 | 万轨实际播放不欠载 |
| Node Worker 离线吞吐 | 真实 Rust 核心在多核 CPU 上生成音频的容量 | 浏览器调度和设备输出稳定、低延迟 |
| 浏览器 AudioWorklet 持续验收 | 该浏览器、设备、配置和操作下的真实消费与欠载 | 其他机器或未来负载均有相同结果 |

当前测量状态见 [VERIFICATION.md](VERIFICATION.md)，以保存的原始报告为依据。已在本机 Edge 155 / Windows / Ryzen 9 9950X3D 实测通过三组配置，均预热 3 秒后持续 60 秒以上，最低 10000 活跃声音、10000 条独立混响轨道、0 启动欠载、0 稳态欠载、0 丢声、非零输出。

| 通过配置 | 预读上限 | 实测在线控制 | 最大控制排队 / 确认 |
| --- | --- | --- | --- |
| **[14 × 256 帧 × 4 块，默认](../benchmarks/edge-realtime-w14-f256-lead4-60s.json)** | **21.33 ms** | **2 次** | **21.33 / 4.255 ms** |
| [8 × 256 帧 × 6 块](../benchmarks/edge-realtime-w8-f256-lead6-60s.json) | 32.00 ms | 3 次 | 32.00 / 8.05 ms |
| [8 × 256 帧 × 5 块](../benchmarks/edge-realtime-w8-f256-lead5-60s.json) | 26.67 ms | 2 次 | 26.67 / 3.465 ms |

选择 14 Worker / 256 帧 / 4 块为默认值，是因为它在此次一分钟长测的通过配置中预读最小。8 Worker 的两组结果作为回退参考。这不表示其他机器、任意系统负载均零欠载，也没有证明全局最低稳定延迟。

保留的失败配置包括旧泵 14 × 128 × 6（27 次稳态欠载）、公平批次泵 14 × 128 × 6（8 次）、14 × 128 × 8（3 次）、8 × 256 × 4（2 次）；均为 60 秒以上测量。原始 JSON 链接集中列在验证记录。这些实际结果说明离线约 4× 吞吐不能代替浏览器持续验收。

## 复现离线吞吐

```powershell
node scripts/benchmark-dsp.mjs --workers 14 --tracks 10000 --frames 256 --seconds 30 --output benchmarks/my-throughput.json
```

参数包括 `--workers`、`--tracks`、`--frames`、`--seconds`、`--warmup-seconds` 和 `--output`；`--help` 显示范围。脚本使用随包真实 WASM，每轨都有循环 PCM 声音、不同速率、增益和声像，混响比例为 20–90%，先预热再计时。报告记录各分片活跃声音、丢声、最后一块能量、峰值、渲染前后内存、混响字节、SIMD、二进制 SHA-256 和机器 / Node / V8 信息。

已执行的两次 30 秒模拟音频结果为：

| Worker | 块长度 | 生成耗时 | 离线吞吐倍数 |
| --- | --- | --- | --- |
| 14 | 256 帧 | 7.002 秒 | 4.284× |
| 14 | 128 帧 | 7.381 秒 | 4.064× |

两次均是 10,000 个活跃循环声音、零丢声、各分片非零输出、渲染内存不增长。原始数据位于 [benchmarks/](../benchmarks/)，具体链接见验证记录。128 帧相对 256 帧的该次吞吐约降低 5%，不能把这一比例直接解释为实时延迟变化。

该脚本不走浏览器 SharedArrayBuffer 消费调度、AudioWorklet 截止时间、声卡输出和编辑 UI。4× 离线吞吐不是“实时零欠载”或“CPU 只占 25%”的承诺；后者还取决于并行线程数、调度、队列和其他任务。

## 浏览器持续验收规则

使用随附本地服务器，在“播放性能”运行至少 60 秒的万轨测试，保存原始报告。测试必须同时满足：

1. 最低活跃声音不少于 10,000，10,000 轨都已启用独立混响，声音池没有丢声。
2. 输出 RMS 非零，避免以空轨道、无声声音或关闭混响代替目标负载。
3. 启动预热与稳态欠载均单独记录，不能只清零后报告稳态数字。
4. 记录浏览器版本、实际采样率、Worker 数、块长度、预读块数、持续时间和输出设备估计延迟。
5. 同样负载下调节单轨混响，并执行选择、滚动、属性和编辑等操作，检查其他轨道独立性、欠载和响应。

页面的压力测试使用持续循环声音，正常歌曲仍按采样自然长度播放。短时自动调优只筛选候选配置，选中的设置还需要持续播放与编辑压力验证。测试会使用大量 CPU，不应与另一组 CPU 压测并行来形成基准结论。

## 延迟与队列

48 kHz 时，128 / 256 / 512 帧块分别为约 2.67 / 5.33 / 10.67 ms。预读队列是 Worker 为吸收系统调度抖动准备的少量未播放音频，不是预先渲染整首歌。实际排队量随消费时点变化。

当前默认 14 Worker / 256 帧 / 4 块的配置预读为约 21.33 ms。测量中设备基础与输出延迟分别约为 10 ms 与 40 ms，须与预读分开理解。环形缓冲物理容量是 32 块，不等于默认排队 32 块。

页面分别显示预读音频、浏览器 `baseLatency` / `outputLatency`、线程 P95 / 最大耗时和控制确认时间。控制确认包含消息调度；控制排队是参数更新可能越过的已生成音频量。它们都不是外部硬件测得的声学往返延迟。调小缓冲可能减少排队，但也更易受到 Windows 调度或后台任务影响。

声音池按分片预分配。提高 `voicesPerTrack` 可以容纳更多采样重叠，但增加内存，不能保证提高 CPU 容量。降低音轨音量也不会减少其独立混响的计算成本。
